## 1. Document Ingestion & Chunking Strategies

| Chunking Strategy | Primary Mechanism | Key Advantages | Disadvantages & Risks | Computational Cost (CPU) | Concurrency / Memory | Applicability to DocuMind |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Fixed-Size Chunking** | Splits text at fixed token or character intervals (e.g. 500 characters) with fixed overlap (e.g. 50 chars). | Simple to implement; zero computational overhead; predictable chunk counts. | Breaks words, sentences, and semantic thoughts mid-stream; high boundary cutoff risk; severe context fragmentation. | Negligible ($< 1$ ms/page on i5 CPU). | Extremely low RAM footprint ($< 1$ MB). | **Naive Baseline only:** Useful for Phase 1 baseline failure reproduction; unacceptable for production. |
| **Recursive Character Chunking** | Hierarchically splits text on prioritized delimiters (`\n\n`, `\n`, ` `, `""`) down to target chunk size. | Keeps paragraphs and sentences intact; preserves local document structure; robust default across document types. | Cannot detect semantic topic shifts within dense prose; boundary heuristics can still split closely tied concepts across chunks. | Very low ($< 5$ ms/page on i5 CPU). | Very low RAM footprint ($< 5$ MB). | **MVP-Critical:** Primary candidate for MVP ingestion; baseline for chunk-size grid search in Phase 2. |
| **Sentence-Based Chunking** | Uses NLP sentence boundary detection (e.g. spaCy or NLTK) to assemble chunks by grouping full sentences. | Guarantees complete grammatical thoughts; zero mid-sentence truncation; clean readability for LLM. | Sentence lengths vary wildly; chunks vary in token size; periods in acronyms/tables cause erroneous splits. | Low-to-Moderate (~15–30 ms/page with lightweight tokenizer). | Low RAM footprint (~15 MB for tokenizer model). | **Version 1.0 Candidate:** Candidate for clean resume and technical report parsing where sentences are well-formed. |
| **Semantic Chunking** | Computes cosine distance between consecutive sentence embeddings; splits when semantic distance exceeds a threshold. | Adapts dynamically to topic shifts; creates semantically coherent topical passages. | High CPU latency (requires embedding every sentence upfront); highly sensitive to arbitrary distance threshold tuning. | High (requires 50–200 embedding forward passes per page; 500–1500 ms/page on CPU). | Moderate RAM footprint (requires holding sentence embeddings in memory). | **Research / Experimental:** Prohibited for MVP due to CPU indexing latency; retained as exploratory spike in Phase 2. |
| **Parent-Child / Hierarchical Chunking** | Generates small child chunks (e.g. 128 tokens) for fine-grained retrieval, linked to large parent chunks (e.g. 512 tokens) for LLM context. | Decouples dense retrieval accuracy (small chunks avoid dilution) from generation context (large chunks provide full context). | Increased indexing complexity; requires two-tier storage (vector index for children + document store for parents). | Low-to-Moderate (linear overhead of storing dual chunk representations). | Low-to-Moderate RAM (requires document lookup table). | **Version 1.0 Candidate:** Target architecture for Phase 2/4 optimization to resolve the retrieval vs. generation granularity trade-off. |

## 4. Dense vs. Sparse vs. Hybrid Retrieval Approaches

| Retrieval Approach | Core Algorithm | Strengths | Weaknesses & Failure Cases | Hardware Resource Impact (CPU) | Complexity | Applicability to DocuMind |
| :--- | :--- | :--- | :--- | :--- | :---: | :--- |
| **Dense Bi-Encoder Retrieval** | Cosine similarity / dot product over 384-dim dense embeddings. | Captures semantic intent, synonyms, and paraphrased concepts; language-model aligned. | Fails on exact keywords, part numbers, acronyms, and rare entities; prone to semantic drift. | Low search latency ($< 5$ ms); requires query embedding forward pass (~20 ms). | Low | **MVP-Critical:** Foundational first-stage retrieval for the MVP pipeline. |
| **Sparse Lexical Retrieval (BM25)** | Term frequency-inverse document frequency with length normalization (Robertson & Zaragoza). | Flawless on exact keywords, code identifiers, proper nouns, and numeric strings; zero training needed. | Blind to synonyms and conceptual phrasing (vocabulary mismatch problem). | Ultra-fast ($< 1$ ms search latency); negligible memory footprint on CPU. | Low | **Version 1.0 Optimization:** Essential component of hybrid retrieval in Phase 4. |
| **Hybrid Retrieval (Dense + BM25 via RRF)** | Fuses dense and sparse rank lists using Reciprocal Rank Fusion ($k=60$). | Combines semantic understanding with exact lexical precision; robust across all query types. | Requires maintaining two indices (vector store + inverted BM25 index); doubles candidate retrieval operations. | Low search latency (~5–10 ms total); easily computed in pure Python on CPU. | Moderate | **Version 1.0 Optimization:** Primary retrieval target for Release 2 to resolve technical vocabulary gaps. |
| **Late Interaction (ColBERT)** | Token-level contextualized embedding bags with `MaxSim` sum-of-max operator. | Exceptional retrieval precision without cross-encoder latency; preserves fine token details. | Massive index size (multiplies storage by 50–100x); heavy RAM consumption; complex indexing. | High memory footprint; prohibitive on 24 GB RAM laptop when scaling beyond thousands of pages. | High | **Research / Experimental:** Deferred; evaluated as theoretical literature only. |

## 6. Generation & Grounding Approaches

| Generation Approach | Implementation Mechanism | Hallucination Control | Citation Verifiability | CPU Generation Throughput | Complexity | Applicability to DocuMind |
| :--- | :--- | :---: | :---: | :---: | :---: | :--- |
| **Direct Prompting (Unconstrained)** | Simple system prompt: *"Answer the user question using the following context."* | Poor: Local LLMs frequently hallucinate external pre-training knowledge when context is ambiguous. | Minimal: Citations are omitted or fabricated unless explicitly enforced. | Fast (standard tokens/sec for local LLM). | Minimal | **Naive Baseline only:** Demonstrates Phase 1 baseline grounding failures. |
| **Grounded System Prompting with Strict Refusal** | System instructions forbidding external knowledge: *"Answer ONLY using facts directly stated in the context. | **Structured Output Schema (JSON / Pydantic)** | Enforces output schema via constrained grammar decoding or Pydantic validation (e.g. `{"answer": "...", "citations": [{"doc_id": "...", "page": 1, "quote": "..."}]}`). | High: Separates answer prose from explicit claim-level source attributions. | High: Every claim is mapped to an explicit document ID, page number, and extracted verbatim snippet. | Moderate: Grammar constraints or schema retries add ~10–20% latency overhead. | Moderate | **MVP-Critical:** Crucial for programmatic UI rendering and citation inspection in Streamlit. |
| **Algorithmic Citation Verification Pass** | Post-generation verification pass: Extracts citation claims and checks textual entailment (NLI) against cited chunks. | Very High: Programmatically strips or flags claims that lack strict entailment support. | Near Flawless: Unverified citations are flagged before display. | Heavy: Requires secondary NLI model pass on CPU (~100–300 ms per claim). | High | **Version 1.0 Optimization:** Planned verification stage for Phase 5 in Release 2. |

## 7. Advanced RAG Techniques

| Advanced Technique | Underlying Mechanism | Expected Benefit | Computational Overhead (CPU) | Primary Failure Modes | Additional Dependencies | Applicability to DocuMind |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Query Rewriting / Expansion** | Prompts LLM to reformulate ambiguous or underspecified queries into standalone technical questions. | Resolves co-references, acronyms, and underspecified terms before retrieval. | Adds 1 full LLM generation call (~1.5–3s on CPU). | Hallucinatory rewriting can diverge from the user's actual intent. | Local LLM prompt template. | **Version 1.0 Candidate:** Target for Phase 6 multi-turn chat; optional in MVP. |
| **Multi-Query Retrieval** | Generates 3–5 alternative phrasing queries; retrieves chunks for all; unions results. | Broadens recall; overcomes lexical phrasing mismatches. | 3–5x embedding queries + 1 LLM generation call (~2–4s total on CPU). | Floods retrieval pipeline with redundant or noisy chunks. | Local LLM prompt + union/dedup logic. | **Version 1.0 Candidate:** To be evaluated in Phase 6 for complex technical queries. |
| **Query Decomposition** | Decomposes complex multi-part questions into sequential sub-queries (e.g. sub-questions 1 and 2). | Solves multi-hop and comparative questions across documents. | Multiplies retrieval and generation calls by $N$ sub-queries ($> 5$s on CPU). | Sub-queries can lose macro-context; error propagation from failed sub-answers. | Planning prompt + aggregator logic. | **Version 1.0 Candidate:** Key technique for Phase 6 comparative and multi-document queries. |
| **HyDE (Hypothetical Embeddings)** | LLM generates a fictitious hypothetical document answering the query; embeds this document for search. | Aligns short query vectors into document embedding space. | Adds 1 LLM generation pass (~1.5–3s on CPU). | If hypothetical document contains false facts, retrieval fetches completely incorrect chunks. | Local LLM prompt. | **Research / Experimental:** Deferred; evaluated as experimental spike in Phase 6. |
| **Corrective RAG (CRAG)** | Evaluator module scores retrieved chunks; triggers web fallback if confidence is low. | Prevents generating from noisy or irrelevant chunks. | Adds confidence scoring pass; external search violates zero-cost/privacy. | Web search leaks private data; confidence classifier errors reject valid chunks. | Evaluator model + web search API (violates constraints). | **Research / Experimental:** Prohibited in external form. Internal confidence gating adapted for Phase 6 abstention. |
| **Self-RAG** | Uses fine-tuned reflection tokens (`[Retrieve]`, `[IsSup]`) to dynamically retrieve and critique answers. | Dynamic on-demand retrieval; end-to-end self-critique. | Requires fine-tuned custom models; cannot run on stock quantized models without heavy prompt emulation. | Off-the-shelf local 3B models struggle with complex multi-token self-reflection prompts. | Fine-tuned weights or complex prompt state machines. | **Research / Experimental:** Retained as academic reference; not feasible for MVP or V1.0 on local CPU. |
| **Conversational Memory State** | Maintains conversation history via sliding window, buffer, or summarized context for multi-turn chat. | Enables coherent conversational follow-up questions across a session. | Low (sliding window) to Moderate (background summarization). | Context window bloat; memory dilution; stale context bleeding into new topics. | In-memory session state manager. | **Version 1.0 Optimization:** Planned for Phase 6 interactive conversational interface. |

## 8. Evaluation Metrics Comparison

| Evaluation Metric | Mathematical Definition / Formulation | Metric Focus | Measurement Type | Minimum Benchmark Sample Size | Limitations & Pitfalls | Applicability to DocuMind |
| :--- | :--- | :--- | :--- | :---: | :--- | :--- |
| **Recall@K** | $\frac{\|D_{\text{relevant}} \cap D_{\text{retrieved@K}}\|}{\|D_{\text{relevant}}\|}$ | Retrieval Completeness | Deterministic Ground Truth | 20–25 (MVP) / 50–100 (V1.0) | Ignores document ordering within the top-$K$; rewards over-retrieval. | **Core Metric (MVP & V1.0):** Primary retrieval benchmark metric. |
| **Precision@K** | $\frac{\|D_{\text{relevant}} \cap D_{\text{retrieved@K}}\|}{K}$ | Retrieval Relevance Density | Deterministic Ground Truth | 20–25 (MVP) / 50–100 (V1.0) | Penalizes systems that return fewer than $K$ chunks even if all returned chunks are relevant. | **Core Metric (MVP & V1.0):** Measures prompt context efficiency. |
| **Mean Reciprocal Rank (MRR@K)** | $\frac{1}{\|Q\|} \sum_{i=1}^{\|Q\|} \frac{1}{\text{rank}_i}$ | Ranking Quality | Deterministic Ground Truth | 20–25 (MVP) / 50–100 (V1.0) | Only considers the rank of the *first* relevant chunk; insensitive to multi-chunk retrieval quality. | **Core Metric (MVP & V1.0):** Primary metric for embedding and reranking evaluation. |
| **nDCG@K** | $\frac{\text{DCG}@K}{\text{IDCG}@K}$, $\text{DCG}@K = \sum_{i=1}^K \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}$ | Graded Ranking Relevance | Deterministic Ground Truth | 50–100 (V1.0) | Requires graded relevance annotations (0–3), which is labor-intensive to label manually. | **Version 1.0 Metric:** Used in Phase 8 reranking ablation studies. |
| **Faithfulness** | $\frac{\text{Number of Claims Supported by Context}}{\text{Total Claims in Answer}}$ | Grounding Integrity | LLM-as-Judge / NLI / Manual | 20–25 (MVP) / 50–100 (V1.0) | LLM judges exhibit self-preference and hallucination; requires strict human-verified ground-truth baseline. | **Core Metric (MVP & V1.0):** Primary metric guarding against hallucination. |
| **Answer Relevance** | Semantic similarity between generated answer and question | Response Utility | LLM-as-Judge / Semantic Sim | 20–25 (MVP) / 50–100 (V1.0) | Can score high on fluent, confident answers that are completely ungrounded in context. | **Secondary Metric (V1.0):** Must always be paired with Faithfulness. |
| **Citation Precision** | $\frac{\text{Number of Valid Citations Supporting Claim}}{\text{Total Citations Generated}}$ | Attribution Accuracy | Deterministic / NLI Check | 20–25 (MVP) / 50–100 (V1.0) | Requires page-level passage mapping in ground truth. | **Core Metric (MVP & V1.0):** Key requirement for DocuMind verifiable source attribution. |
| **P50 / P95 Latency** | 50th and 95th percentile wall-clock response time (ms) | Operational Efficiency | Automated Hardware Profiling | 20–25 (MVP) / 50–100 (V1.0) | Varies with background OS load; requires multiple warm runs on standardized CPU hardware. | **Core Metric (MVP & V1.0):** Critical benchmark under local i5-1135G7 CPU constraint. |
| **RAM Footprint** | Peak resident set size (RSS in MB) | Memory Hygiene | Automated Process Profiling | 20–25 (MVP) / 50–100 (V1.0) | Must distinguish between model weight allocation and memory leaks during batch loops. | **Core Metric (MVP & V1.0):** Ensures application runs comfortably within 24 GB RAM. |
